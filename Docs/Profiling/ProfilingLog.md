## 2단계. 실기기 측정

### 기준을 바로잡음
- `11`: 처음에는 Profiler Highlights의 목표를 **60fps**로 둔 채 봐서 거의 모든 프레임이 초과로 보였다.
- `14`: 실제 빌드는 30fps라서 목표를 **30fps**로 바꾸고 다시 판단했다.
- `15` `16` `17`: Call Stacks 옵션이 켜져 있어 `Profiler.Callstack`이 최대 92ms까지 끼어 있었다. **Profiler 자체의 비용**이므로 끄고 다시 측정했다.

### VSync와 Present 이해
- `10` `12` `13`: 대기 마커가 항상 짝으로 나온다. 메인 스레드의 `VSync` / `WaitForTargetFPS`, 렌더 스레드의 `GfxDeviceVK.Present`.
- Present는 비용이 아니라 **대기**. 무엇을 기다리는지(GPU인지, 30fps 제한인지)는 같은 프레임의 GPU Time으로 판단한다.
- Vulkan에서는 일부 프레임의 GPU Time이 `--`로 빠질 수 있다. GPU 값이 있는 프레임을 골라야 한다.

### 스파이크 (Call Stacks 끈 상태)

## 3단계. 공격 스파이크 다시 보기 (2026-10-15, 직접 확인)

어제 진단은 "공격 순간 `AttackTrigger` 스파이크 = 타격 이펙트 Instantiate"였다. Call Stacks를 끈 캡처(19-32, 19-37)로 다시 펼쳐 봤다. Hierarchy 드롭다운을 **Raw Hierarchy**로 바꾸면 같은 이름의 `Instantiate`가 합쳐지지 않아 하나씩 볼 수 있다.

### 19-32 캡처 1125프레임 — 막타
| 스크린샷 | 본 것 | 판단 |
|---|---|---|
| `31` | `AttackTrigger` Total 7.52ms, **Self 4.55ms** | 하위 항목은 약 3ms뿐. 대부분이 Self |
| `32` | `Instantiate` 3회 합 2.54ms (Produce · Copy · Awake) | 3회가 전부 이펙트인지 확인 필요 |
| `33` | `Instantiate.Awake` 아래 `ItemPickup.Awake` 0.81ms, `AudioPlayer.Awake` | 적이 죽으면서 드랍 아이템과 소리가 같은 호출 안에서 생성됨 → **막타 프레임** |
| `34` `35` | Raw Hierarchy로 3개 분리: 1번 아이템 1.75ms, **2번 이펙트 0.54ms**(Copy 0.28 + Produce 0.16 + Awake 0.08), 3번 소리 | 이펙트는 Awake 아래에 스크립트 없이 렌더러 항목만 있어 구분 |

### 19-37 캡처 342프레임 — 일반 공격
| 스크린샷 | 본 것 | 판단 |
|---|---|---|
| `36` `37` | `AttackTrigger` Total 4.05ms, **Self 2.04ms**, `Instantiate` 6회 합 약 1.8ms | 막타가 아니어도 Self가 절반 |

### 배운 것
- **Self** = 자기 아래에 마커로 잡히지 않은 모든 시간. `AttackTrigger()`는 `OnAttackTrigger?.Invoke()` 한 줄이라, 구독자 함수들의 시간이 전부 Self로 합쳐진다. 호출 방식(Action vs UnityEvent)의 비용은 마이크로초 단위라 원인이 아니다.
- 풀링하면 Instantiate의 Produce · Copy · Awake가 없어지고, 꺼낼 때 `SetActive(true)` → `OnEnable` 비용이 남는다.
- `Instantiate`의 Self가 0인 건 정상이다. 시간은 자식에서 쓰므로 Total을 본다.

### 진단 (직접 작성)
- 풀링할 생성 비용(이펙트 · 아이템 · 소리)도 있지만 **Self가 더 크다.**
- Self 안에 무엇이 들어 있는지는 지금 캡처로는 더 볼 수 없으니, `OnAttackTrigger` 구독자에 `ProfilerMarker`를 달고 다시 측정해 확인한다.
- 이펙트만 풀링하는 것으로는 부족하다. 범위는 마커 결과를 보고 정한다.

## 4단계. 장면별 GPU 비교와 실험 계획 (2026-10-15, 직접 확인)

### Bottlenecks 다시 읽기
- `38` (19-32 캡처 전체): GPU 88% / CPU 0%가 목표 초과. `39` (18-34 캡처 전체): GPU 5% / CPU 2%.
- **Bottlenecks %** = 선택한 프레임 중 그 장치(CPU 또는 GPU)가 목표 시간(33.3ms) 안에 일을 못 끝낸 비율. 다 그리고 쉬는 시간은 VSync · `WaitForTargetFPS` 같은 대기 마커로 따로 나온다.
- 범위를 캡처 전체로 잡으면 지역 이동(로딩) 구간이 섞인다. Rendering 그래프가 끊기거나 계단처럼 바뀌는 곳이 지역 이동이므로, 평평하게 이어지는 구간만 고른다.
- Median 프레임 시간(36.7ms / 33.3ms)은 30fps 제한에 묶여 있어 GPU 차이를 잘 보여 주지 않는다.

### 그릴 게 더 많았나 (각 캡처 300프레임, Rendering 모듈)
| 캡처 | GPU 목표 초과 | Triangles | Vertices |
|---|---|---|---|
| 19-32 | 88% | 700.5k | 848.1k |
| 18-34 | 5% | 203.8k | 143.1k |

19-32가 삼각형 약 3.4배, 정점 약 6배. "그릴 게 많아서 GPU가 목표보다 오래 걸렸다"는 가설과 맞는 방향이다. 다만 두 장면 비교라서 원인이라고 확정할 수는 없다(삼각형이 많은 장면은 그림자 · 풀 · 나무도 많다) → 실험으로 확인한다.

### 배운 것: GPU 비용의 두 덩어리
| 항목 | 줄이는 것 | 분류 |
|---|---|---|
| MSAA | 픽셀당 샘플 수 (정점 · 삼각형 수는 그대로) | 픽셀 |
| 렌더 스케일 | 그리는 픽셀 수 (0.7이면 약 절반) | 픽셀 |
| 포스트 프로세싱 | 다 그린 화면을 한 번 더 칠하는 작업. 물체 수와 무관, 픽셀 수에 비례 | 픽셀 |
| 그림자 | 빛 시점에서 장면을 한 번 더 그림 (캐스케이드 수만큼) | 지오메트리 |

### GPU 실험 계획 (직접 작성)
렌더 스케일은 원인이 아니라 원인을 가려내는 도구다. 픽셀 비용 전체를 줄이면서 삼각형 수는 그대로 두기 때문이다.

렌더 스케일을 1.0 → 0.7로 낮췄을 때(픽셀 약 절반)
- GPU 시간이 **많이** 줄면 → 픽셀 쪽 비용이 병목이다. 다음 실험은 포스트 프로세싱을 건드려서 한 번 더 그리는 작업을 잡아 본다.
- GPU 시간이 **거의 안** 줄면 → 원인은 다른 곳(지오메트리 쪽)에 있다. 다음 실험은 그림자를 끄는 실험을 해서 그릴 것을 줄여 본다.
